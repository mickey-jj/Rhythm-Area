## 4. Scala 后端的严格写法限制

### 4.1 使用不可变值，禁止可变变量

**依据：L2 p29。**课件明确要求在系统中不要使用变量，并区分 `val` 与 `var`。

本项目执行要求：

- 使用 `val`、不可变数据和返回新值的方式表达计算过程。
- 不使用 `var` 保存并反复修改业务状态。
- 通过产生新值保留计算步骤，不依赖被覆盖的中间状态。

**容易漏掉的情况：**`val` 只保证引用不能重新赋值，不保证引用的对象不可变。L2 p28 将 `ListBuffer` 加命令式循环的写法与 `.map` 作对比。因此本项目也不通过 `val` 包装可变集合来绕开不可变原则。这是对课程原则的落实，PPT 没有逐项列出所有可变集合类名。

这一条出现在 Scala 教学部分，不应机械扩张成“前端 TypeScript 中一切局部赋值语法都被老师禁止”。前端另有第 7 节的状态管理规范。

### 4.2 禁止命令式 for 循环，以集合变换表达处理

**依据：L2 p31–33。**p31 明确写“我们不准使用 for 循环”，推荐 `map`、`flatMap`、`filter`。

- 集合转换用 `map`，筛选用 `filter`，组合或展开用 `flatMap`、`flatten` 等。
- 不使用循环加可变缓冲区逐项积累结果的写法。
- 课件没有逐项声明 `while` 等关键字禁令，但不应借助其他命令式循环绕开同一项纯函数式要求。

**重要边界：Monad 的 `for ... yield` 不能一概禁用。**L3 p5 的 `Try` 截图，以及 p25 的 Cats Effect 截图，都明确展示了 `for ... yield`。p25 同时展示了 `flatMap`、`for ... yield` 和 `>>` 三种组合方式。

因此，本项目按以下证据解释：禁止命令式循环；可以使用基于 `map` / `flatMap` 的 Monad 推导式。不能只搜索 `for` 关键字就判定违规。

### 4.3 不使用直接的 try / catch / finally 处理方式

**依据：L3 p3–5。**p3 明确说明 `try, catch, finally` 不是类型安全的，“我们课程不使用”；随后介绍 `Option[T]` 和 `Try[T]`。

- 缺失值以 `Option[T]` 表达，区分 `Some` 和 `None`。
- 对课件所示的可能失败的同步计算，可使用 `Try[T]` 表达成功或失败。
- 已经处于 `IO` 中的操作，使用效果类型提供的错误处理方式组合，保持失败在效果链中。具体库方法属于实现选择，不是 PPT 逐字规定的 API 名称。
- 不把所有错误吞掉并伪装成成功。

**截图与文字的边界：**L3 p4 的 `Option` 说明截图内部出现 `try/catch`，用于解释转换函数，但不能据此忽略 p3 明确写出的课程限制。本项目实现以明确限制为准，不照抄这一段底层实现。

### 4.4 用领域类型组织业务，避免基本类型混用

**依据：L3 p8–11、p15。**课件强调找出系统最根本的元素，通常用 `case class` 定义对象，再用这些元素组合业务对象；p11 写有“不要使用基础类型”。

本项目据上下文解释为：**不要用缺乏业务含义的 `String`、`Int` 等贯穿领域接口，导致不同概念混用。**例如用户 ID、日记 ID、订单 ID 应有各自的领域含义，复合对象应由这些类型组成。

不能将这一句解释为禁止代码中出现任何基本类型：L2 p30 教授基本类型，L3 p8 的 `Book(isbn: String)`、p9 的枚举截图，以及 L4 的数据库示例都继续使用基本类型。

本项目执行建议：

- 实体与组合对象优先用不可变 `case class`。
- 有限状态、类别优先考虑 `enum`，见 L3 p9。
- 对容易混淆的标识符等定义有语义的类型；并非给每一个临时整数都机械加一层包装。
- JSON、数据库和外部输入可以使用基础表示，但应在边界与领域类型之间清楚转换。

## 5. 纯函数、Monad 与副作用边界

### 5.1 核心逻辑必须按纯函数组织

**依据：L3 p13–15。**课件给出的纯函数特征包括：输出只依赖输入、相同输入得到相同结果、没有副作用。

- 校验、计算、过滤、业务规则、数据转换等核心逻辑，尽量以输入到输出的纯函数表达。
- 数据库读写、人机交互、网络通信等属于副作用，必须推到边缘处理。
- 不让核心计算偷偷依赖数据库、网络、可变全局状态或执行时刻。
- 函数式处理数据与面向对象定义类型可以互补，不是禁止使用 `class`、`trait` 或对象建模，见 L3 p10、p15。

其中关于时间和全局状态的检查，是“输出只依赖输入”原则的具体应用，不是课件另列的一组关键字禁令。

### 5.2 后端 API 生成 Monad，由框架执行

**依据：L3 p17–25，尤其 p24。**课件明确写整个项目基于 Monad 实现，后端 API 生成完整 Monad，“我们自己不执行，是后端框架默默负责执行”；系统功能基于纯函数式框架。

本项目执行要求：

- 用效果类型描述有副作用的计划，采用课件所介绍的 Cats Effect `IO`。
- 使用 `map`、`flatMap` 等组合相关步骤，不能为了取得中间结果而在业务处理过程中手动执行效果。
- API 的处理流程返回组合好的效果值，由后端框架的运行入口统一执行。
- 数据库、网络、文件、日志等有副作用的调用放入适当的效果边界。

项目检查时，应特别关注请求处理链中手动执行 `IO`、把效果执行结果写入全局可变变量、或在构造效果值之前已执行副作用的情况。不要把这个检查扩大成“整个应用不能存在运行入口”，应用仍需要框架在最外层执行效果。

“整个项目基于 Monad”的原文出现在 Scala/后端 API 的教学语境中。前端按照 React 与 Hooks 的章节实现，不能据此要求所有 React 组件返回 Cats Effect `IO`。

## 6. 后端模块、API、数据库与序列化

### 6.1 微服务按职责拆分，不要求多个部署进程

**依据：L4 p2–4。**每个微服务应有明确的名字、数据库和 API 功能，拆分原则是高内聚、低耦合。

- 先说明每个模块负责什么、管理什么数据、提供什么 API。
- API 由模块定位决定，用来处理相关数据或完成某类运算。
- 避免同一业务规则分散在多个不相关模块中，或模块之间随意互相访问内部实现。
- **课程明确允许“逻辑上分开，实现上合在一起”**，并说明课程推荐框架可以不考虑微服务间传输，见 L4 p4。

因此现有材料没有要求固定数量的微服务、每个微服务独立部署、每个服务一个物理数据库，或引入容器编排。约 10 个网页也不等于 10 个微服务。

### 6.2 复杂类型跨边界时做统一序列化

**依据：L4 p4–7。**复杂对象与字符串表示之间需要统一转换，课件介绍 Circe 的 Encoder / Decoder。

- 前后端或模块之间交换复杂数据时，建立明确的编解码约定。
- 数据库的基础类型直接存储；复杂类型可以序列化为文本，也可以考虑 JSON。
- 课件举例 `List[Int]` 可用数据库整数数组，`List[T]` 可存 `text`；p7 又展示了标识符列表使用 `BIGINT[]`。不能将例子简化成“所有列表都必须存 TEXT”。
- 序列化是边界表示，不意味着领域层必须放弃有语义的复杂类型。

### 6.3 数据表应有清楚的类型与关系

**依据：L4 p11–12。**每列有自己的类型，主键唯一，外键联系其他表的主键。

- 按业务实体设计字段和关系，保证类型匹配。
- 课件推荐每张表有主键；不能自行改成“所有表都必须使用自增整数主键”。
- 需要关系时清楚表达关联；并未要求每一张表必须有外键。
- 初始化 SQL 的 `SERIAL`、`TIMESTAMP`、`TEXT`、`BIGINT[]` 等是教学示例，不必原样复制表名和字段。

**本项目执行建议：**核心业务数据通过后端持久化到数据库，刷新页面及重启后仍能按设计读取。数据库初始化方式随源码提供。这个检查用于证明项目形成完整前后端系统，并非 H2 另列的一条“必须通过重启测试”的评分原文。

## 7. React 前端的状态与代码组织限制

### 7.1 明确区分常数、核心数据、展示型数据

**依据：L5 p3–6。**课程用 MVC 和时间变化解释前端，要求明确定义数据与展示关系。

| 数据类别 | 含义 | 项目处理方式 |
| --- | --- | --- |
| 常数 | 不随时间变化 | 定义为常量，不作为任意可写的共享状态。 |
| 核心数据 | 用户或外界会修改的关键状态 | 使用 React Hooks 管理；需要跨页共享时可用 Zustand。 |
| 展示型数据 | 依赖核心数据计算得到的内容 | 由纯函数关系推导，随着核心数据变化而变化，不成为随处独立修改的状态。 |

View 应当是数据的函数。先明确用户真正修改哪份核心数据，再确定哪些内容由它推导。避免为同一事实维护多份可独立修改的数据。

这一原则不等于“不能使用 `useEffect`”。L5 p10 明确介绍 `useEffect`，并给出更新页面标题、加载数据及随依赖变化更新值的示例。本项目应按实际依赖和副作用边界使用它。

### 7.2 纯计算函数与组件分开

**依据：L5 p6。**

- 纯计算函数有输入、有输出、不返回 HTML 组件，也没有副作用，用于数据到数据的转换。
- React 组件返回页面组件，通过 Hooks 或常量取得渲染所需数据。
- 课件明确强调没有全局变量。结合 Zustand 章节，应理解为不能依赖脱离 React 响应机制的随意可变全局状态，而不是禁止模块级常量或封装后的共享 store。
- 纯计算不读取 Hooks；有副作用的交互和同步行为推到合适边缘。

### 7.3 Zustand 的 hook、快照、更新接口不得混用

**依据：L5 p7–9。**课件列出三种操作：

| 接口形式 | 作用 | 应注意的限制 |
| --- | --- | --- |
| `useXXX()` | 订阅会随时间变化的核心数据 | 用于组件渲染相关的取值；普通纯计算函数中不要调用。 |
| `getXXXSnap()` | 取得某一时刻的值 | 这是快照，不构成响应式订阅；不能用它代替组件渲染所需的 hook。 |
| `setXXX()` | 更新对应核心数据 | 统一经公开的更新接口修改，不到处直接操作 store。 |

L5 p8 明确写：“纯函数中不要加 useXXX”“组件中不要加 getXXX”。本项目落实时，要让组件的显示值随状态变化更新。事件处理等确需一次性快照的逻辑，应与渲染订阅区分。纯计算函数仍优先通过参数接收数据，不能因为没有使用 Hook 就认定偷偷读取全局状态也是纯函数。

L5 p9 给出的两项使用建议：

- 名字尽量长而清楚，减少混用。
- **store 私有化，只公开 use / set / get 函数**，便于追踪所有用途。

本项目按这一封装方案实现共享状态。课件同时提醒全局核心数据容易滥用，因此不把每一个页面局部字段都放到全局 store。

### 7.4 跨页传参有多种方式，页面过长要模块化拆分

**依据：L5 p12–13。**

- 跨页共享的全局核心数据可用 Zustand。
- 组件或面板可通过函数参数 / props 接收所需数据。
- 跳转可携带 Location 数据，新页面可通过 `useLocation` 读取。
- 以上是可选方式，不是每页必须同时使用的三项任务。
- 页面代码过长时按模块拆分，每个模块可包含自身结构、样式和逻辑。
- 课件没有规定每个文件的最大行数，也没有要求 HTML、CSS、JS 必须各自独立一个文件。

## 8. 容易误读或错误追加的要求

| 容易产生的误读 | 本项目应采用的解释 |
| --- | --- |
| 有 `for` 关键字就违规 | 禁止命令式循环；L3 p5、p25 有 Monad `for ... yield` 示例。 |
| 写成 `val ListBuffer` 就满足不可变 | 引用不可重新赋值不等于内容不可变；仍须检查可变数据与副作用。 |
| 禁用 `try/catch`，所以必须忽略异常 | 应把缺失和失败放到合适类型或效果中处理。 |
| “不要基础类型”意味着不能出现 `String`、`Int` | 重点是领域建模；课件自己的 case class 和数据库示例使用基础类型。 |
| 纯函数式意味着数据库读写也不允许 | 允许必要副作用，要求封装并推到边缘。 |
| 禁止前端全局变量，因此不能用 Zustand | 课程明确介绍了 Zustand，要求克制使用并封装共享状态。 |
| 每页必须用 Zustand，或组件显示数据用快照 getter | 局部状态不必全局化；组件渲染使用响应式 hook。 |
| 所有展示数据都要用 `useEffect` 存一份 | 先明确核心数据与推导关系；课件并未要求全部派生内容都复制成独立状态。 |
| 约 10 页意味着必须 10 个微服务、独立部署 | 页面数量与服务数量无对应要求；逻辑拆分、合并实现有明确课件依据。 |
| 必须使用 Tailwind，不能写普通 CSS | 课件同时介绍普通 CSS、Flexbox、Grid 和 Tailwind，没有这项禁令。 |
| 必须严格锁死 Scala 3.4.2 等所有示例版本 | Scala 明确允许其他 3.xx；其他工具需区分示例与推荐。 |
| 必须继承 HW1 的 IP、视频背景和 2 页结构 | L2 p35 明确属于第一次作业；不能移植成 HW2 的强制项。HW2 自己要求的是约 10 页和本人录制的使用流程。 |
| HW1 已经有日记网站，所以直接提交即可 | 现有 HW1 README 描述的是两页纯前端、`localStorage` 存储。可以复用主题或素材，但若沿用它，需要补足 HW2 的系统范围与后端实现。 |

### 10.1 直接交付要求

- [ ] 附件不超过 100M；本项目按视频加源码总量留余量控制。（H2-05）

### 10.2 实现约束

- [ ] 按 TypeScript + React、Scala 3 和课程纯函数式路线实现。
- [ ] Scala 业务代码不使用 `var`，不靠可变集合保存并修改中间业务状态。
- [ ] 不使用命令式 `for` 循环；Monad 的 `for ... yield` 按实际语义判断。
- [ ] 不直接采用 `try/catch/finally` 的业务错误处理写法。
- [ ] 核心业务逻辑只依赖输入，无隐藏副作用。
- [ ] 数据库、网络等副作用封装到效果中，后端 API 返回组合后的 Monad，由框架执行。
- [ ] 领域对象有清楚的类型，重要业务概念不以无差别的基础值混用。
- [ ] 模块职责、数据库归属、API 定位清楚；不为页面数量机械增加服务。
- [ ] 前端区分核心与展示数据，纯函数和组件职责分开。
- [ ] 不在纯计算函数中使用 Hooks，不以快照 getter 代替组件的响应式取值。
- [ ] 如使用 Zustand，共享 store 私有，公开命名清楚的 use / set / get 接口。
- [ ] 页面过长时按业务模块拆分，实际代码项目位于英文路径。
